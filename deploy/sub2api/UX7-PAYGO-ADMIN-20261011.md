## 用户需求与实现

| 用户需求 | 本次实现与边界 |
|---|---|
| 用户列太宽、空白、无昵称或头像 | 用户列限制宽度，昵称优先，登录账号独立展示，首字头像；缺失信息回退登录名/邮箱/ID。后端批量补齐当前页的登录名，避免昵称重复占据登录账号列。头像是可用的昵称首字头像，没有虚构个人照片。 |
| 平台管理应管理全部团队 | 独立 `/admin/teams` 全团队列表，包含 ID、名称、队长昵称、人数、状态和搜索；选中后管理该团队成员昵称、限额、状态、移除及邀请。平台管理员服务端拥有管理权限，普通队长不能越权。 |
| 手动调整个人/团队订阅 | 用户操作菜单“调整订阅”；支持个人、新团队、已有自有团队的授予、每周额度/有效期调整、取消。团队页也可进入。必须填写原因，保留前后值与操作者，重复提交不会重复授予。 |
| 团队已用周额度修正 | 管理员独立折叠操作，支持明确归零；周周期/旧值/版本校验，正常用量变化或预留中的请求会阻止冲突修改。不改累计用量、成员消费、钱包或历史调用。 |
| 点击个人导航不收起平台导航 | 折叠状态保存在应用 store；初次根据路由展开，此后页面切换不覆盖用户选择。 |
| 调用记录沿用旧顺序 | 时间 → ID/昵称 → 个人/团队资金范围 → 模型 → 输入/输出及缓存 → 人民币费用 → 首字/耗时 → 详情；保留模型图标、头像、紧凑筛选和手机卡片。 |
| 绿黄红性能标记 | 首字时间、耗时/速度按阈值显示细侧线；缺少历史测量值用未知状态，不能编造首字时间。详情保留原始值。 |
| PAYGO“充10到账10” | 订单记录人民币现金和固定到账快照，原生钱包精度保留；不加手续费、赠送或兑换交互。工作台余额旁为普通蓝色充值入口。 |
| 恢复原 ZPay 商户 | 原生 EasyPay 驱动显式 `compatibilityMode=zpay`，按官方 GET 查询订单，严格验证签名和真实商户查询结果，再用原生幂等入账。商户启用需独立记录，更新 EXE 本身不会开放支付。 |

旧需求来源包括 2026-10-08 会话 `01a11af2-4ad0-7a92-939f-9ee6e85b86f8`、`01a109f3-54c1-7280-b6a6-34d62ca1dab0` 以及旧 `realyu-team-funding-lab`：管理员操作入口、团队命名、个人/团队周权益、有效期、周剩余与使用修正。保留默认 28 天及总额度为周额度四倍的合同语义；调整周额度不清空已用和周期，取消仅改变状态。

**明确边界：**此订阅管理操作针对 RealYu 托管资金身份，不把原生邮箱用户的 `user_subscriptions` 当作该账本；非托管用户不可在此授予。已有有效团队成员申请新团队时必须先处理原成员关系，不自动移除并撤销旧团队 Key。个人 Key、钱包和历史不受新团队授予影响。

## 数据库与发布

309 将订单的原生额度数值拓宽到 `numeric(26,8)`，人民币实付列仍保留分精度，不重算旧订单或钱包。310 添加团队 ID sequence 和管理员权益操作审计/幂等表，不导入历史、重置余额或复制 Key。

现有已审 `singlecore_payment_update.py` 仅适用于本机确定的 UX5/300 项基线；引用已经过隔离恢复核验的备份，所有脚本/源码/程序/迁移均由计划固定。入口排空最多 30 秒；未排空则开门退出，不停服务。启动失败时只在同一 PG 权威上恢复已固定的 UX5 EXE，保留已审增量结构；**禁止恢复发布前数据库覆盖新增交易**。支付保持关闭，且初次更新要求没有余额充值订单。开始新交易后不能随意用旧流程回退。

新服务器按 [整站迁移入口](SERVER-MIGRATION-START-HERE-20261011.md) 从固定上游和补丁重建，形成自己的干净提交、私有计划、服务目录和哈希。不要执行开发机 `Activate-Ux*`，不要使用旧 308 校验器验收已完成 309/310 的库。迁机取当前完整 PG 和必要 Redis 状态，不重跑旧 SQLite 客户导入。

## 发布后必验清单

1. 实际 EXE 哈希、Session 0 服务、302 项完整 migration、ACTIVE 与开门回执；PG/Redis 权威未切换。
2. 公网直连/经 SG、backend、bridge、两 Tunnel 的真实内容和采样新鲜度；保留首错，不能只看 ready=200。
3. 原管理员登录、用户昵称/登录名/头像、全部团队清单；普通用户/队长的越权拒绝。生产可只读验证，资金写入案例在隔离库完成。
4. 个人/团队历史与趋势对账、模型标识、Token/缓存、首字/耗时及未知历史显示；320/390 手机、英文与暗色、键盘和侧栏展开行为。
5. 用原商户配置原生加密 provider，确认支付宝显示与限额、人民币实付/到账、回调地址、订单快照；不触碰客户余额或伪造商户回调。
6. 真实小额下单取得支付页；用户实际支付后检查公网回调、商户查询、订单 completed、一次入账和余额前后差；重复通知不再到账。用户未付款时必须记为 `WAITING_FOR_PAYMENT`。
7. 原 Key 模型列表、至少一次完整流式响应/账务及必要 WS 续聊；未测试项单列，不借旧版测试宣称此次全量通过。
