# UX9：已付款订单的 ZPay 查单解析修复

本页记录 2026-10-12 的真实充值故障。最终发布身份和订单恢复结果见 [LIVE](../../LIVE-DEPLOYMENT.md) 及 [验收证据](../../lab/sub2api_e2e/ux9-zpay-20261012.json)。历史 UX7/UX8 的“未实付”描述属于当时的测试边界，不能替代本次实付核对。

## 原因及修复

用户实付人民币 5 元后，商户查单显示已支付，但原生订单仍待支付。11:47:49 CST 公网回调已经抵达 `/api/v1/payment/webhook/easypay`，请求 ID `c3296168-5b5c-450f-982f-a2c7a6957f97`；后端报 `invalid ZPay query response`，返回 400。后续自动补单同样失败。不能将此事件归为没有收到回调或代理断连。

对同一商户、同一订单的只读复现发现：不带 Accept 的请求返回 JSON 对象；带原生驱动实际发送的 `Accept: application/json` 时，返回包在 JSON 字符串中的对象。Go 原生请求经代理、直连及指定 User-Agent 均复现字符串包装。原来的测试只模拟对象，先前 Python 商户探测也没有复现该请求头。

修复仅在 ZPay 查单边界兼容一层字符串包装，然后必须解析为对象。继续校验商户、订单、支付状态、现金金额、支付方式，以及通知签名与独立查单的一致性。拒绝数组、null、标量、多层字符串、尾随数据、错误商户/订单、缺失状态和非整分金额。没有添加 SQL 补余额、跳过验签、伪造回调或修改订单现金的路径。

## 实际测试

新增包装响应回归在修复前确实失败，随后完整 provider 包通过。真实隔离 PostgreSQL 的19项充值、购买和历史根回归通过；原生 HTTP 建单/签名通知覆盖用户名和邮箱两种登录来源，以及对象/包装对象两种商户响应。每组含八个并发重复通知、金额不一致拒绝、未收到成功通知后的自动补单与重复补单不重复入账。

补充过期两小时且尚未保存商户流水的原生拥有者查单恢复、错误金额拒绝和重复核验测试通过。本次没有改动原生过期资金规则；这不等于所有过期或退款状态都能无限恢复。补充测试首轮仅出现 int 与 int64 断言类型不一致，修正后全部通过。

Vite 与 Windows Go 程序构建通过；最终程序携带干净源码提交，完整交付补丁从固定上游复原 435 文件并逐项核对。最终 EXE 的隔离 `/api/status` 确认为 UX9。前端内容没有修改，因此未把之前的视觉测试或模型调用计入此次新验收。

## 发布与迁机

使用已有无 schema 变更的原生更新器，在当前 PG 权威上更换程序。未排空则自动撤销维护，不杀现有流；失败只可回退同一 PG 上的程序，不恢复旧数据库。第一次 30 秒排空及第二次 60 秒排空超时记录保留；一次重复安装目录被预检拒绝，没有关闭入口。已结束的操作及已写入的安装目录不能当作可重放计划。

新机继续从部署分支执行 `Prepare-SingleCore.ps1 -Destination NEW_DIRECTORY -Build -Test`，以 `singlecore-source.json` 固定上游和完整补丁。必须迁移最新 PG 的支付订单、充值使用记录、审计记录、provider 和稳定加密密钥，以及必要 Redis 状态。真实订单已有资金结果，不能用发布前快照覆盖。

遇到已实付待入账时，先独立查单核实真实付款、金额和商户，再使用原生订单拥有者的 verify 或现有自动补单流程。保留第一次通知错误；重复核对必须仍只有一笔入账。不能因为当前页面显示成功，就声称实际通知重试也已获得 200；真实通知重试与自动查单恢复是不同证据。
